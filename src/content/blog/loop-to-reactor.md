你交给 Agent 一件要跑两天的事：改代码、提交、跑构建、等人看一眼、等发布审批。

它前面跑得很快。分析、动手、提交，几分钟的事。然后它停下来。

接下来的十五分钟它在等 CI。再往后，它要等一个人看代码，可能是半天。如果碰上发布审批，它得跨过一个周末。这中间真正"动手"的时间加起来，可能不到十分钟。剩下的全是等。

等本身没问题。问题是让它怎么等。

一种常见的做法是留着那条会话，让它挂在那儿。或者起个后台任务，隔三十秒问一次 CI。还有更常见的：什么都不留，等人回来再问一句"过没了？"——于是人在聊天框里打出"CI 过了吗"的那一刻，其实不是在使用它，是在替它做调度。而调度这件事，本来就该归机器管。

我第一次意识到这件事有点严重，是因为一个跑长任务的 Agent 把同一个问题问了我两遍。它不蠢，它每一步都对。我却以为它会一直记得——想得美。问题出在它等的那段时间里，"我在等什么"这个信息**没有地方放**。挂过一次，丢过一次，只好再问。

等待没有宿主。

## 一、这个形状，我见过

说来也巧，二十五年前的服务器就是这么死的。

那时候一个连接一条线程。线程很贵，栈一兆起。一万条连接进来，内存先崩。可你要问这些线程在忙什么——什么都没忙，它们百分之九十九的时间在等一个网络包回来。

后来所有人都知道了答案：别让"等待"占着一条命。把"我在等什么"登记进一张表，线程全部下班，包来了按登记叫人。这就是 Reactor，今天的高性能服务器没有一个不是这么活的。

有意思的地方在于，Agent 世界正在重演这场迁移，连病灶的形状都一模一样。但账本换了，换出两样当年没有的东西。

**第一样，唤醒是有价签的。**

CPU 收到一个包，顺手跑个处理函数，微秒级，没人心疼这点开销。Agent 一醒可就是一次模型调用：钱、延迟，还有权限面——因为醒来不只是"看见了"，还可能"动手做"。所以那句老话在 Agent 这里必须补半句：事件到了，不等于立刻花钱。CPU 的事件循环从不需要这句话。这句话是 Agent 时代的新物种特征——唤醒之前，得过一道门。

**第二样，分发不再靠查表。**

事件循环问的是"哪个连接有数据了"，一次查找搞定。而 Agent 收到一条 GitHub 评论，要回答的却是：这是哪个工作的？该不该放下手头的活？这个结果会不会已经过期了？没有哈希表能回答这些。这是语义判断。所以 Agent 版 Reactor 里那个"该叫醒谁"的环节，要么是一张写死的规则表，要么是一个便宜的小模型——总之它不是免费的。

## 二、同样是等十五分钟

等待住在哪，决定了它是资产还是债务。

住在人身上的等法最古老：你回来问，它答一句。简单直接，但人是闹钟，人是调度器。

住在进程里的等法看起来先进：它挂着，轮询，自主推进。可这其实是拿钱换幻觉——轮询烧 token，挂着占内存，进程一重启，等待凭空消失。

住在一张表里的等法最安静：它写下一行"我在等 CI #42"，然后人和机器全走开。结果回来了，精准叫醒它。中间什么都没消耗。

![三阶段迁移：Loop / Thread-Session / Reactor 与等待的三种宿主](/images/blog/loop-to-reactor/three-stages.png)

三种等法的差距不在聪明程度，在宿主。等待住在人身上，系统离不开人；住在进程里，系统怕重启；只有住在表里，它才真正变成可以清点、可以接管、可以活过周末的东西。

## 三、一个容易搞错的地方

说到这里，很容易顺势推出"所以 Agent 应该改成事件驱动"——对，但不全对。

Reactor 不是来替代循环的。一轮执行内部还是那个循环：想、动手、再想。变的只是轮与轮之间的空白。空白从"挂住的一条命"，变成"一行记录"。

用并发的术语讲，身份和执行的关系，就是 goroutine 和 CPU 的关系。看起来一直活着，其实是一份认知，被许多次短暂的执行轮流点亮。每次点亮是一次呼吸。呼吸之间，它不在任何进程里，它在表里。

这也是为什么在提示词里写一百遍"你要主动推进"都没什么用。主动性不是性格，是系统前提。它得知道有活是自己的，得能感知到外面发生了什么，得能记着自己干到哪了。三样都缺，它就只能等着你戳一下——油瓶倒了也不知道扶，不怪它，它没长眼睛。

## 四、那张表里写什么

说穿了就几件事，但每一件都是被真实事故教出来的。

得写清在等什么，而且要对得上号。"等 CI"不够，得是哪次构建，结果回来了要验明正身。否则一条迟到的消息就能把它从坟里叫醒，带着过期的假设继续干活——这比不醒还糟。

得写清什么算到了。超时算什么，过期还算不算，这些不能等出了事现场想。

不同的等待要分开对待。定时器到点就该醒；任务结果回来了要核对；人的输入最特殊，人不理你就一直等着，**绝不自动重试**；外部消息可能迟到、重复、乱序，得防着点。把这几种混在一个布尔值里，就只能在每个角落硬编码超时。

醒来还得接得上。一个 Agent 一睁眼就问"我是谁、干到哪了"，说明它醒来时抱错了上下文。续体就是它的进程控制块，少了它，每次唤醒都是一次失忆。

## 五、这套东西不解决什么

诚实划个边界，免得三个月后自己再发明一遍。

"这条消息该归哪个等待"，依然是语义问题。机制只保证匹配可判定，不保证匹配得对。

短交互别上这套。序列化、事件调度都是开销，一次性的问答就该用最朴素的循环。这场迁移只发生在长程层。

还有个更冷的事实：这套结构让你可靠、可审计、可恢复，但它不让你更聪明。能力来自模型和工具，架构只负责让能力稳定兑现，并且说清它做了什么。把卖点押在聪明上的系统，迟早被模型的进步碾平；把卖点押在结构上的，模型越强它越值钱。

## 结语

我现在看一套 Agent 系统，不问它用了什么框架，只问两句。

等待住在哪里？唤醒值多少钱？

第一个问题答"住在进程里"，那是 C10k 之前的服务器。答"住在表里"，才算过了第一关。

第二个问题答不上来，说明唤醒还是一种免费的幻觉。而幻觉这个东西，在系统里迟早会变成账单，或者事故。

杀掉所有进程，它不应该失去任何东西。十年前这句话是对操作系统说的。

现在，是对 Agent 说的。
