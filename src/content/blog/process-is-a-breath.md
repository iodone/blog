你交给一个 Agent 一个要跑三天的任务：改一百个仓库的依赖，每改完一个跑一次测试，失败就修，修不动就停下来问你。

第一天它跑得很好。第二天早上你打开窗口，它在等——等你回答一个它昨晚就该问的问题。你回了，它继续。半小时后你发现两件事：同一个问题它问了两遍；那批依赖，它在第三个仓库上装了一次，又装了一次。

它不笨。它昨天做的每一步都对。问题出在别的地方：**它记不得自己做过什么、正在等什么、还欠这个世界什么。**

这篇文章想回答一个问题：如果抛开一切现成实现，从最顶层重新设计一个 Agent，应该从哪儿开始？

答案是：**不要从能力开始，从约束开始。**

而且，一旦你认真接受那几个约束，剩下的架构几乎没有设计自由度。它长成什么样，是被逼出来的，不是被设计出来的。

先把结论放在这里。这是全文的骨架，后面所有内容都只是它的展开。三个词各管一段：**系统**是它要承受的世界，**结构**是东西必须住的地方，**架构**是推到最后剩下的那张图纸。

- **系统层**——它必须承受三个物理事实：进程会死；动作不可逆，而连接不可靠；一个主体、多个位置、一份记忆。
- **结构层**——于是有了四条分离：状态不住在执行里；意图先于结果落盘；事实、认知、投影不能混为一谈；权限不绑执行位置。九个名词。等待必须变成一行数据，不能挂在调用栈上。
- **架构层**——这三件事互相咬合，逼出一条因果链：从「进程会死」一路推到「唤醒不等于授权」。权限是五道门的交集。落到图纸上，崩了会真丢的只有三样：历史、认知、未决。推到最后你会发现，「要不要这样设计」已经不是问题，「能不能不这样」才是。

先从第一个问题开始：它到底要承受什么。

---

## 一、系统：它必须承受什么

任何一个跑得够久的系统，最后都会撞上同一组事实。它们不是工程选择的后果，是物理。把它们列出来，是因为设计的一半工作就是把约束写清楚——约束不清楚，后面每一个决定都会变成口味之争。

### 事实一：进程会死

任务的寿命是「天」和「周」，进程的寿命是「秒」和「分」。

云主机会重启，容器会被回收，网络会抖，一次部署会把你所有活着的进程换掉。这些都不是故障，是常态。所以有一句话必须先说清楚：

> 任何只存在于进程里的东西，在架构上等于不存在。

这句话听起来像洁癖，其实是判据。设计时对每一份状态都要问一遍：**进程死了，它还在吗？** 不在的东西，就得想办法搬出去。

### 事实二：动作不可逆，而连接不可靠

发出去的钱追不回来。改掉的远端配置不会因为你的连接断了就自动恢复。世界是有记忆的，而且是只追加的。

麻烦在于另一头：**「断线」和「没发生」，在你这一侧看起来一模一样。**

你发出一条命令，然后连接断了。你不知道它是发出去之后断的，还是根本没发出去就断了。这不是一个可以靠重试解决的问题——**重试在这里不是「再试一次」，而是「可能做两次」。**

### 事实三：一个主体，多个位置，一份记忆

你会希望它能在你的笔记本上动手、在测试机上动手、在生产真机上动手。这是很自然的诉求——任务在哪里，手就该伸到哪里。

但你不会希望它变成三个「你」。三个「你」意味着三份记忆、三种判断、三套权限，以及迟早会出现的三个互相矛盾的结论。

这三个事实不是三个问题。它们共享同一个错误前提。

### 病根：我们把「进程」当成了「存在」

把它们排在一起，病根就露出来了。只要你觉得「进程就是它本人」，下面每一件事都会自动发生：

| 前提 | 于是 |
|:---|:---|
| 状态住在进程内存里 | 重启就失忆 |
| 等待挂在调用栈上 | 进程一死，等待凭空消失 |
| 记忆活在上下文窗口里 | 除了压缩对话记录，没有别的办法 |
| 执行节点就是 Agent 本人 | 每台机器都要部署一个 Agent——于是「像病毒一样，复制一份、渗透进每台机器」这个直觉出现了 |
| 连接断开是「它的事件」 | 于是可以「换台设备重发」 |

反过来陈述，就是整套设计的地基：

> ### 进程是一次呼吸，不是一条命。
>
> 一个 Agent 一生要呼吸几万次。如果每一次呼吸都是它的全部，它就没有一生。

这句话不是审美偏好，是那三个物理事实的算术结果。接下来的部分，全是它的推论。

## 二、结构：存在必须落在哪里

系统层说的是「必须承受什么」。结构层说的是：**既然要承受这些，那么什么东西必须住在哪里。**

结论是四句话：状态不能住在执行里，意图不能住在结果之后，事实、认知、投影不能混为一谈，权限不能绑在执行位置上。这四句话，叫作**四条分离**。

### 分离一：状态不能住在执行里

想象两个世界。

一个是**状态世界**：它活得比任何一次会话都长，载体是持久存储，是唯一真相，随时可以重建。另一个是**执行世界**：它由进程、沙箱、远端机器组成，寿命是秒到分钟，**全部可以抛弃**。

判据很干净：把执行世界整个抹掉——杀掉所有进程，销毁所有沙箱，断开所有连接——状态世界必须仍然完整可读，并且能据此继续工作。

这里有一个非常好用的反例判据。如果有人告诉你系统「可以多起几个实例」，你只需要问一句：**多起之前，要不要先搬一个本地卷？**

要搬，那这个系统其实只有一份状态住在一台机器上，多实例是假的。

### 分离二：意图不能住在结果之后

这一条是四条分离里最贵的，也是收益最大的。

凡是对外界留下真实痕迹的动作——写盘、发消息、付钱、改远端——叫它**外效**。一次外效在时间上分三段：

![外效窗口：崩溃落在哪一段，决定系统答不答得出「命令发了没有」](/images/blog/agent-continuity/external-effect-window.svg)

②之前崩溃，什么都没发生。③之后崩溃，一切都已经记录。真正的问题在①②和②③之间那两段：**动作可能已经发生，而你没有任何记录。**

天真的系统在这种时候会做一件看起来最合理的事：「没收到结果，那就重发一次吧。」然后就有了重复副作用。

正确的做法只有一条：**在执行之前，先写一条意图记录。** 它有身份，绑定当时那个确切的执行者，带幂等键，状态可查询。于是「不知道」被替换成三种可判定的状态：

| 你观察到 | 判定 |
|:---|:---|
| 有意图记录，没有执行记录 | **未开始**，重新派发是安全的 |
| 有执行记录，还没结算 | **进行中**——可能已经发出，绝不能重发 |
| 有执行记录，已经结算 | **已完成**，结果可重放 |

于是有了那条必须记住的纪律：

> **连接断开，不等于命令没有执行。**
> 因为无法区分，所以「换个地方重发」是被禁止的动作。正确动作是把这条意图标为未决，等它由事实了结。

这三行，就是「意图先于执行」的全部理由。没有第一条记录，「没发」和「发了没记」永远无法区分——于是系统只能在重复副作用和丢结果之间随机选一个。

### 分离三：事实、认知、投影不能混为一谈

继续往下切。刚才那个意图记录属于「发生过什么」。但「我发生过什么」和「我认为现在是什么」是完全不同的两件事。

这件事分三层，各答一个不同的问题：

| 层 | 它回答 | 能不能改 |
|:---|:---|:---|
| **历史层** | 发生过什么？ | 只能追加，不能改 |
| **认知层** | 我认为现在是什么？ | 可以改，但要留下版本和来源 |
| **投影层** | 这一轮能看见什么？ | 每轮现算，随时可以丢掉重算 |

一句记法：**历史是相片，认知是笔记，投影是今天带出门的那几页。** 相片不能改，笔记可以改，带哪几页出门每轮自己挑。

最容易犯的错，是把「发生过什么」和「我认为什么」放进同一个命名空间。那样一来，「我改主意了」就会悄悄变成「历史被改了」。

这里是整个设计里最锋利的一条判据：

> **「读到历史证据」和「声明当前认知」永远是两个动作。**
> 看见一条历史记录，不等于拥有了这个结论。要把它变成自己的认知，必须显式声明一次。

为什么三层不能合并成一条对话流？因为它们**天然失配**：历史是单调增长的，认知是可以被推翻的，投影是有界的。硬塞进一条流里，就一定会出现某一刻，用错误的层去回答一个正确的问题——今天多数 Agent 的失忆和幻觉，机制上就来自这里。

顺带纠正一个几乎所有人都会犯的错误：**省上下文预算，不该靠压缩历史，该靠缩小投影。** 压缩是不可逆的、无法定位的；缩小投影是每轮重新决定的，改完就恢复。

### 分离四：权限不能绑在执行位置上（正交，不是分层）

前三条是**分层**——它们叠在同一个主体上。第四条不是，它是一条**正交**关系。这是全文最容易搞错、也最要命的一处。

> **「在哪儿做」和「该不该做」是两个正交问题。**
> 把它们绑在一起，是绝大多数越权漏洞的机制性来源。

- **决策轴**问的是：该不该做？它由身份、沙箱、审批策略、能力授权决定。
- **执行轴**问的是：在哪儿做？它是本机、受管远端、薄执行末梢、还是真机。

一句话，逐字记住：

> **选择执行地点，不等于授予权限。**
> 换一个节点动手，权限不会因为「换了个地方」而扩大。授权只会被收窄。

这句话有三个推论，每一个都能独立地干掉一批错误设计。

一、**「云端 Agent」不是一种架构。** 它只是执行轴上的一个取值。把执行点从本机挪到远端，权限模型一个字都不用改。所以「内核和记忆在云端，执行可以在任何节点」这句话是对的，但它描述的是**正交**，不是「云端」——真正带来安全性的，是两个轴分开了，不是执行点搬到了云上。

二、**执行末梢不需要完整智能。** 它接收指令、校验、执行、回报就够了，它不维护第二份认知。这一条直接否掉了「像病毒一样自我复制」那个直觉——末梢是末梢，不是子代。

三、**一个主体可以有很多只手，但只有一份认知和责任。** 这就是那句我最想让你记住的话：

> **智能可以是不连续的，责任必须是连续的。**

四句话放在一张图里：

![四条分离合起来：一份认知，许多具可抛弃的身体](/images/blog/agent-continuity/four-separations-combined.svg)

同一份认知，许多具可抛弃的身体。身体不拥有认知，只在授权范围内动手，然后把事实交回来。

### 状态分三层，名字也要分两套

分层之后有一个容易被忽略但要命的细节：**命名空间不能共用。**

历史层按**会话**分卷（一段对话一卷）——因为对话的真相属于「这段关系」。认知层按**主体**键——因为结论属于「这个主体」，一个结论要能跨会话存活。一条会话的历史，没有资格替主体表态。

### 名词只有九个

结构收敛到最后，需要的东西出奇地少。九个名词，没有第十个——这是「如无必要，勿增实体」的硬约束，不是清单的凑数。

| 名词 | 是什么 | 关键约束 |
|:---|:---|:---|
| **主体** | 记忆与责任的所有者 | 跨会话存活 |
| **会话** | 一段持续的关系 | 历史按它分卷 |
| **线程** | 一条工作线 | **执行点绑在它身上，不绑会话** |
| **目标** | 要达成什么 | 绑线程，不绑会话 |
| **激活** | 一次执行机会 | 用完即弃，不持有认知 |
| **等待** | 正在等什么 | 独立成一条记录，有匹配键和到期条件 |
| **意图** | 打算做的外效 | 动作前落盘，幂等，可查询 |
| **执行点** | 动手的物理位置 | 与权限正交 |
| **事实** | 已发生的事 | 不可变 |

两个非常容易装错的地方，值得单独说：

执行点**绑线程，不绑会话**。否则「换个会话的默认设备」会悄悄改掉一个**已经在跑的线程**的落点——这类 bug 极其隐蔽，因为每一步看起来都是对的。

目标也**绑线程**。目标不是会话的属性：会话可以换，工作线不该因此丢掉目标。

### 等待住在表里，不住在进程栈里

这套结构里还有一个反直觉的推论，它来自一个简单的事实：**Agent 的时间几乎全在等。** 等一次 API 返回，等一个人批准，等一个构建完成，等一个外部事件。

等的时间占九成，想的时间占一成。而我们今天把等待写在了哪里？写在调用栈里。

这意味着：**系统里最长的那部分，恰好是最不可靠的那部分。** 一个进程从开始等的那一刻一直活着，死一个进程就丢一个等待。

换个说法，性质就变了：

| 说法 | 机制 | 后果 |
|:---|:---|:---|
| ❌「一个实习生坐在机房里，把电话按在耳朵上等」 | 一个进程从等待开始一直活着 | 死一个进程，丢一个等待 |
| ✅「把『我在等什么』写进登记簿，没事干的人全部下班」 | 等待是一行记录，没有专属进程 | 崩溃后可以枚举所有未决等待 |

于是就有了那句口诀：

> **等待住在表里，不住在进程栈里。**

判断一套执行模型成不成熟，不问它用了什么并发模型，只问一句：**「等待住在哪里？」**

答「调用栈」——每个等待都占一条命，超时、重试、崩溃都要额外机制去补救。答「状态里」——等待是一行数据，可查询、可枚举、可审计、可回收。

还有一种进程是必要的：**长驻的认知进程**。它会一直在，但它的方式是「真阻塞、零 CPU」，不是轮询。它身上不持有状态，所以**随便重启**。除定时之外，所有等待都不该有专属进程。

## 三、架构：为什么只能长成这样

到这里，结构已经摆出来了。但结构本身不解释一件事：**为什么必须是这个顺序。**

这是「架构」这一层要回答的。它不关心有哪些部件，只关心谁逼出了谁。

### 一条因果链

想象你从唯一那个物理事实出发，一步步往下走：

![一条因果链：每一步都是上一步逼出来的](/images/blog/agent-continuity/causal-chain.svg)

这条链的读法不是「我们实现了六个机制」，而是：因为进程会死，所以等待必须独立；因为等待独立，所以它需要匹配规则；因为需要规则，所以类型和匹配键要分开；因为分开，才能把「要不要花钱」的决定权收回来；因为收得回来，才有降级空间；因为能降级，等待才不会自动变成账单。

断任何一环，整条链就退化回「每个等待一个进程」的旧模型。

| 断在哪 | 退化结果 |
|:---|:---|
| 等待不是对象 | 崩溃即丢等待，只能靠超时兜底 |
| 唤醒没有匹配 | 任何一个事件唤醒所有等待 |
| 匹配键等于类型 | 同类事件互相误唤醒 |
| 匹配即授权 | 任何事件到达都自动重进模型，成本失控 |
| 没有降级路径 | 分不清「值得思考」和「只是动了一下」 |
| 没有成本闸门 | 唤醒频率直接等于账单 |

### 拿崩溃当测试场

同一条链，放进崩溃这个测试场，三个断点各自暴露一条纪律：

| 崩溃点 | 世界状态 | 天真系统会做什么 | 正确处置 |
|:---|:---|:---|:---|
| 意图已写，执行未派发 | 什么都没发生 | 无从判断 | 重新派发（安全） |
| 意图已写，执行已派发，结果未回 | **可能已发生** | 「重发一次吧」→ 重复副作用 | **绝不重发**，标未决，查证了结 |
| 结果已回，认知未提交 | 已发生，未记录 | 结果丢失，或重复提交 | 结果可重放，认知靠版本校验重试 |

第二行是全部理由所在。没有那条意图记录，它永远无法和第一行区分。

### 「成功了」是一句危险的话

还有一个必须拆掉的东西：**「这轮成功了」**。你几乎每天都在说它。

这句话把四件毫不相干的事压成了一个词。拆开是四个边界，每一个失败的含义都不一样：

| 边界 | 问题 | 失败意味着 |
|:---|:---|:---|
| 模型输出 | 响应拿到了吗？ | 模型失败，通常可以重试 |
| 工具执行 | 动作在世界上发生了吗？ | **不可重试**，只能查证 |
| 状态提交 | 认知被接受了吗？ | 版本冲突，需要重读重试 |
| 结果交付 | 结论送出了吗？ | 交付失败，任务没完成 |

不拆，排障时你只能回答「这次运行挂了」。拆了，你才能回答「是没发、发了没记、记了没存，还是存了没交」——后者才是修复的依据。

顺带一个语义上的硬规定：**没有「做完了但没交」这个状态。** 完成必须同时满足条件和送达，两者是同一个终点。

### 权限是一个交集，不是并集

最后一个结构性推论落在权限上。

一个动作要落地，必须**同时**穿过五道门，全过才放行：谁在请求；这台机器允不允许这类事；隔离边界允不允许；这一步需不需要人批准；这张带有效期的许可证覆不覆盖这个动作。（为什么是交集、不是并集？并集等于「过一道门就算过」，那等于没有门。）

两条铁律：

- **默认拒绝。** 任何一维不确定，就不许落地。
- **授权只收窄。** 不匹配时的默认动作是「降到最便宜的处置」，不是「放行」。

这里有一条和「等待」联动的规则，很容易被忽略：**唤醒不等于授权。** 一个事件到达，可以决定「唤醒哪个等待对象」；但要**不要重新进入模型**，是另一件事。这两件事必须分开——否则任何到达的事件，都能间接地替 Agent 扩容权限。

反过来看，这条规则也是一个成本刹车，而且是整套设计里最实用的一个：**事件到了，不等于立刻花钱。**

### 落到图纸上

上面每一条都是被逼出来的。把它们摆到一起，落地之后长这样：

![落地结构：一份权威留在中枢，许多可抛弃的手伸到前线](/images/blog/agent-continuity/deployment-structure.svg)

图里三处值得停一下。

第一处是左右那条边界划在哪里。它不划在「本机 / 云端」，也不划在「内网 / 公网」，而是划在**「能定义真相的」和「只能动一下手的」**之间。因为划在这里，末梢才可以有 N 个、主机才可以天天换，而整个系统里配得上「它认为」三个字的东西，始终只有一份。

第二处在左边内部：**崩一次会真丢东西的，只有历史、认知、未决这三样**，其余全是无状态重算——注意别和分离三的「三层」弄混：那三层里的投影永远不权威（每轮现算，可丢），第三处权威是**未决**，也就是「还欠世界什么」。这条线直接决定了运维的全部动作——要备份的就这三样，要扩容的只有右边，要重启的只有中间那些不持状态、因此也不需要名字的部件。

第三处是两个面之间那根细线：**向下只有「指令 + 一张收窄的授权租约」，向上只有「事实」。**（租约就是五道门里那张带期限的许可证。）没有第三条通道，也没有反向的一票。末梢看见什么、自己琢磨出什么，都不会变成中枢的认知；除非它先作为事实被记下来，再由中枢显式声明一次。

这张图不是画出来的，是推出来的——每一条线都对应前面一条约束。结构到这里就闭合了。

## 四、终局：可托付

前面三节都在讲结构。但如果有人问「这套东西到底为了什么」，「为了更聪明」不是答案。

> **终极目标 = 把智能的执行做成不连续的，把智能的责任做成连续的，从而得到一个可以托付的 Agent。**

「可托付」不是形容词，是可以判定的。它由五个子性质构成，每一个都对应一个能被追问的问题：

| 性质 | 能回答才有 | 依赖 |
|:---|:---|:---|
| **可审计** | 每一个结论，能追到是哪些历史事实、经哪次修订得出的吗？ | 三层分离 + 来源记录 |
| **可回放** | 抹掉所有进程、只留事实，能重建出「当时我认为什么」吗？ | 历史层唯一权威 |
| **可强制** | 给定一条策略，能在动作发生**之前**拦住它吗？ | 执行前门槛 |
| **可迁移** | 换一台机器、换一个模型、换一个执行点，责任和记忆跟着走吗？ | 状态 ⊥ 执行 |
| **可恢复** | 崩在最坏的时刻，能判断「哪些意图没有了结」并安全继续吗？ | 意图先于执行 |

最后一条是前四条的联合压力测试：它同时考验能不能定位未决意图、能不能重建现场、恢复时是否仍受策略约束、以及恢复能不能换一台机器完成。

反过来，有三个目标要显式排除，因为它们会把你带偏：

- **「更聪明」**——结构改善的是可审计性，不是正确性。这是设计选择，不是局限：把卖点押在聪明上，长期一定会被模型进步碾平。
- **「更高的任务完成率」**——完成率是模型和工具的函数。架构贡献的是可靠性，是同样的能力能不能稳定兑现，不是能力的上限。
- **「更好的基准分数」**——基准是结果，不是设计输入。为了让架构可辩护去优化基准，是本末倒置。

于是一句话划清边界：

> **能力来自模型和工具；架构只负责让能力可靠地兑现，并且可靠地说清「它做了什么」。**

## 五、这套东西不解决什么

一个架构设计如果不写清「它不解决什么」，它会在三个月后被自己重新发明一遍。这一节是整篇里最舍不得省的部分。

「一个到达的事件该归给哪个等待」——这类语义判断，目前没有好答案。该唤醒还是该排队、过期的结果该不该丢，本设计只保证匹配是纯比对、可判定，不保证匹配得对。

成本可见性也只有一半。唤醒频率乘以模型调用是唯一的账单闸门，但「每唤醒一次该花多少」没有先验。长驻架构最容易在这里失血。

多主体协作，只给了原则，没给协议。多个主体交接工作时怎么摩擦最小，关键不在发明一种新的通信协议，而在设计好「谁能读到什么」——那是一条读取策略，不是一个通信协议。

权限的语义粒度仍然是个语义问题。五道门给了结构，但「这张授权覆不覆盖这个动作」要靠语义判定——相似不等于相同。

提示注入没有被消灭。执行前门槛削弱了它（未审的动作不可调度），但没有根除它。凡是模型能读到的内容，都可能试图改变它的判断。

还有一条更硬的证据，单独放在这里：

> 我复盘过一个把确定性内核做到极致的实现——事务、冲突分类、近千个测试——在标准基准上，与最强的现成 Agent **打平**。

它说明一件残酷的事：

> **内核是入场券，不是护城河。**

先拿资格（可靠、可审计、可恢复），再谈差异（聪明）。这句话不是谦辞，是因果：架构改善的是可审计性，不是答案的正确性。那份复盘的作者总结得更干脆——**「结构化的表示可以提升可审计性，而不提升答案准确率。」** 这是设计者自己划的界，不是别人给的批评。

也正因为如此，有几条路不建议走：不要为了让 Agent「持有个性」去包裹现成的 SDK，那会让出控制权；不要让「知识」里带可执行代码；不要照搬成熟分布式系统的拓扑（协议可以抄，拓扑不能）；不要状态还没真正离开进程，就上多节点调度。还有一条最隐蔽的：**不要为了省上下文预算去压缩历史。**

### 一个必须换掉的隐喻

写这篇文章之前，我一直在用一个说法：「云端 Agent 应该像病毒一样渗透到宿主的执行环境里。」

这个隐喻必须换掉。两个理由：

**本体错了。** 病毒会自我复制，每个副本自治。而执行末梢不复制、不自治、不持有第二份认知——它是**末梢**，不是**子代**。

**权限错了。** 更麻烦的是，「病毒」这个说法会把你自动带向节点自治：每个节点自己决定该做什么。这直接违反「授权只收窄」，也是最容易写出越权漏洞的那条路。

合适的说法是：

> **中枢 + 末梢。**
> 中枢是连续的认知与责任；末梢是它在物理世界的手，可插拔、可替换、不持有意志。

这不是措辞偏好。**用什么隐喻思考，决定权限模型往哪边倒。** 用「病毒」想，你会自然写出节点自治；用「中枢 + 末梢」想，你会自然写出「只接收、校验、执行、回报」。

## 六、结语

三句话收尾。

> **哲学**：进程是一次呼吸，不是一条命。所以智能可以不连续，责任必须连续。

> **结构**：四条分离——状态 ⊥ 执行、意图 ⊥ 事实、事实 ⊥ 认知 ⊥ 投影、决策 ⊥ 执行。前三条是分层，第四条是正交。混同这一处，权限模型就会走偏。

> **终局**：不是更聪明的 Agent，是可托付的 Agent——可审计、可回放、可强制、可迁移、可恢复。

最后，一个可以随身带走的判据。

判断一个 Agent 架构成熟没有，不必读它的设计文档，问五个问题就够了：

1. 杀掉所有进程，重启后能不能列出**所有未了结的意图**？
2. 三个月前的一条结论，能不能追到它的来源和修订历史？
3. 有没有**一个**地方，能在动作发生前拦住它？
4. 把执行点从 A 换到 B，权限会不会变大？
5. 「正在等什么」能不能被**枚举出来**，而不是「跑起来才知道」？

五个都能明确回答，架构成立。三个以下——那就还是在把进程当存在。

> **杀掉所有进程，它不应该失去任何东西。**

今天多数系统做不到。做不到的原因通常只有一个：**等待和意图，没有宿主。**
