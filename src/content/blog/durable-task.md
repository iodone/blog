你让 Agent 调研三个方案，完成实现，再找另一个 Agent 审核，最后交给你确认。

半小时后，你去开会；三个小时后，服务重启了一次；第二天，你补充了一条约束。回来时，你希望看到的是一个交代：现在由谁负责，已经做到哪里，正在等谁，哪些结果能用，哪些外部操作还没有确认。

很多系统只能给你一个转圈的图标。

它不傻，每一步可能都做得对。只是它把一件要活几天的工作，交给了一个随时可能消失的调用栈。连接一断，页面不知道任务还在不在；进程一死，等待和接管都失去凭据；重试一来，旧结果又可能覆盖新指令。

Durable Task 要解决的正是这件事。它不是一个“永不退出的后台进程”，而是**一件工作跨连接、跨进程、跨实例的持续责任**。

这个区别决定了系统的形状。要从终态往下推：如果计算随时会停，责任就必须有另一个住处。

## 一、面向终态：你要的不是进程活着，而是工作有着落

一件长任务的理想状态，不是界面上永远有一个“运行中”。它应该随时能回答六个问题：目标是什么，当前由谁负责，已经做到哪里，正在等谁，哪份结果可以信任，停止之后还有哪些账没有了结。

这六个问题把 Durable Task 和普通后台任务分开了。后者关心一次程序有没有跑完，前者关心一件工作有没有被持续负责。

由此可以得到三条边界。

**计算可以暂停，责任不能暂停。** 服务重启、模型超时或执行者被替换，只终止一段计算，不应抹掉目标、等待和未决结果。

**等待是一种事实，不是一种占用。** 等人回答时，系统不必让一个进程抱着请求空等。它需要记住等谁、为什么等、什么条件可以继续，以及等待何时过期。

**取消是一种交接，不是一种遗忘。** 系统要阻止旧执行继续写入，也要承认外部操作可能已经发生。关闭连接只能说明页面不再观看，不能证明任务已经停止，更不能撤销已经发出的邮件或订单。

这套终态并不要求某个具体界面。它要求的是：无论界面怎样呈现，系统都不能靠一个活着的进程来证明自己还在负责。

## 二、概念模型：把一件工作拆成责任、委托和执行

要承载这种责任，最自然的产品对象是“事项”，而 Durable Task 是它背后的执行视图。事项回答“要做什么”，Task 回答“系统如何持续负责”。它们是同一件工作的两个视角，不是两套需要分别维护的台账。

![事项、Durable Task、阶段、委托与执行代际的概念关系](/images/blog/durable-task/concept-model.svg)

一件工作可以按阶段推进：先实现，再审核，最后验收。每个阶段通过一次 **Assignment（委托）** 交给执行者，通过一次或多次 **Attempt（执行代际）** 完成当班计算。

Task、Assignment 和 Attempt 的寿命并不相同。Task 跨阶段存活；Assignment 把某个阶段的责任交给明确的执行者；Attempt 只描述一段可以中断、重试或替换的计算。这样，换执行者不必新建事项，崩溃接管也不必把旧工作复制一遍。

另外三组概念让时间本身变得可管理。**Wait** 记录等待关系；**Result** 记录交付内容，**Receipt** 记录执行怎样结束、留下了哪些证据；追加式历史保存发生过什么，长期记忆保存当前形成的结论。历史只能追加，认知可以修订，二者不能互相冒充。

这里最容易混淆的是“接管”和“重试”。接管只替换当班写者，工作仍是同一代；重试或新指令则可能开启新的业务执行代际。把二者压成“再跑一次”，系统就分不清继续旧工作和执行新意图。

## 三、持久边界：保存继续负责所需的事实

有了这些概念，Durable 的含义就可以说得更准确：保存的不是进程的完整内存，而是继续负责所需的事实。

其中至少有四类：目标、阶段、委托与验收权构成的**责任**；当前 Attempt、有效写者与取消意图构成的**执行身份**；等待条件、未处理事件与结果回执构成的**交接状态**；以及可追溯的**历史与认知**。

![持久事实层保存责任与交接状态，临时执行单元按需启动和退出](/images/blog/durable-task/persistence-boundary.svg)

这张图里没有画具体数据库或进程框架，因为它们都可以替换。真正不能替换的是权威边界：协调职责只从持久事实恢复，执行单元只负责当班计算。进程监督、消息驱动和故障隔离依然有用，但它们解决的是一次计算怎样运行，不自动带来跨实例的持续责任。

持久化也有明确的极限。它不能让被杀掉的工具进程原地复活，不能让模型从半个 token 继续生成，也不能自动知道外部 API 在断线前是否已经执行。恢复的是责任与协调状态，不是时间旅行。

## 四、运行机制：每一次交接都必须有凭据

静态分层只说明状态住在哪里，真正的设计要在时间线上接受考验。创建、完成、等待、崩溃和取消，分别对应一种交接。

### 创建与完成：先形成事实，再通知世界

创建事项时，系统先保存原始输入，再整理目标，建立 Task、初始阶段和委托。身份、权限与上下文由服务端补齐，创建协议支持幂等。模型可以表达“要创建什么”，不能自行宣布权限已检查、事实已提交。

完成一次 Attempt 时，结果与回执、执行终态、协调者待处理事件必须在同一个事务里提交。提交成功后，系统才尽力发送通知。通知只是门铃，持久事件才是事实；通知可以丢失或重复，消费逻辑仍必须能对账、能幂等。

### 等待：登记关系，释放执行

传统做法让请求和进程一起挂着，Durable 的做法是先写入 Wait，标记等待，释放当前写者，让执行单元退出。回答到达后，系统找到对应 Wait，记录回答及来源，并留下协调事件。

因为继续工作的依据在事实里，不在原进程的调用栈里，任意可用实例都能接手后续协调。等待由“占用一个执行者”变成了“保存一条可以恢复的关系”。

### 崩溃：接管责任，同时更换写入权威

真正困难的不是启动一个新实例，而是处理那个可能只是变慢、并没有死掉的旧实例。系统需要一张有时效的 **Lease（写入许可）**，以及单调推进的 **Epoch（写者代际）**。

![崩溃接管：新实例以更高写者代际接管，旧实例的迟到结果只能留作证据](/images/blog/durable-task/writer-handoff.svg)

旧实例停止续租后，写入许可到期，新实例接管同一 Attempt，并以更高的 Epoch 继续。它读取责任、等待、结果和历史，接着承担未完成的工作。旧实例后来即使恢复，也只能提交历史证据，不能再覆盖当前状态。

这里要把两种代际分开：重试、中断或新指令推进业务执行代际；崩溃和接管推进写者代际。前者意味着工作意图变了，后者只意味着当班者变了。

还需要一道执行隔离：旧模型响应、旧工具结果即使晚到，也不能混入新回合或触发旧工具。**慢，不等于死；但过期，就意味着失去权威。**

### 取消：先封存旧权威，再核对真实世界

取消先成为持久意图，随后关闭旧 Attempt 的等待，禁止它继续提交权威结果，再尽力停止仍在运行的计算。最后系统必须读回真实状态：哪些已经停止，哪些仍在等待，哪些外部结果尚未确认。

如果外部结果未知，就先对账，不能盲目重放。Durable 能保证系统不遗忘这笔悬而未决的账，却不能替外部世界提供回滚。

## 五、状态语义：三个“完成”，谁也不能冒充谁

长任务最容易被一个“完成”掩盖三种不同事实。

**执行提交**只说明某次 Attempt 交回了结果；**业务验收**说明结果被审核并被有权者认账；**外部结算**说明真实世界里的副作用已经确认。代码生成成功不等于测试通过，测试通过不等于用户验收，请求断线也不等于外部操作没有发生。

因此，业务状态、执行状态和外部结算状态需要分别保存。它们可以在产品上被整理成清楚的下一步，但不能被压成一个绿色的“完成”。否则，系统会把执行者的自我报告当成事实，把用户的沉默当成验收，把连接中断当成安全重试的许可。

## 六、判断标准：把所有进程停掉，看它还能交代什么

一套 Durable Task 设计是否成立，不看它能否让一次演示从头跑到尾，而看它在不连续的世界里能否继续交代。

停掉所有计算进程之后，系统能否列出仍存活的事项、各自的等待、未处理结果和未决外部操作？旧实例恢复后，它的结果会不会覆盖新指令？等待回答时进程能否退出，回答到达后能否唤醒正确的工作？执行失败会不会留下永远运行中的假象？

这些问题都能回答，Durable 才不是一种存储装饰，而是一种责任模型。

它保存的不是一个永不退出的进程，而是系统在任何一次执行结束之后，仍然能够说清楚：一件工作从哪里来，现在由谁负责，下一步凭什么继续。

进程可以换，连接可以断，计算可以暂停。责任不能因此消失。
